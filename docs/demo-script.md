# Ringio Demo Script

This script is designed for a 6–8 minute reviewer demo. Never present mocked data as devnet state. Ringio renders only decoded devnet Group/Member/vault state and shows empty/error when none can be verified. The program, config, and first Group values below are explorer-verifiable; later lifecycle placeholders remain explicitly untested.

## Demo promise

Show one idea clearly: Ringio turns a familiar savings circle into an inspectable state machine, and directly covers the dangerous case in which an early recipient stops contributing.

Do not claim that collateral guarantees liveness. A pre-payout member can still stall the MVP.

Current repository cut: the Bauhaus UI, wallet connection, deterministic/optional-AI discovery over direct devnet account reads, non-signing previews, SBF/IDL build, public program/config initialization, real Group creation, and read-only agent manifest are implemented. Scene 2 can use live state. The browser-side transaction actions in Scenes 3–7 remain previews; only the first `create_group` has external-script explorer evidence.

## Scene 1 — The problem (0:00–0:35)

Show the landing/dashboard hero.

Suggested narration:

> Savings circles work because people know each other, but the ledger and payout order are usually informal. The dangerous moment is after an early member receives the pot: they still owe future contributions. Ringio makes the rules and funds visible on Solana and protects those post-payout obligations with rank-aware collateral.

Point to the three product truths: invite-only roster, fixed USDC terms, and transparent recipient order.

## Scene 2 — Find a fitting public group (0:35–1:20)

Use Ringio Guide in the Bauhaus discovery panel. Ask in Turkish or English for a budget, cadence, and member count, then show the returned public group code, fit reasons, tradeoffs, contribution, and open seats. Look up one exact `RNG-XXXXXXXXXXXX` code and state:

> The code is derived from the Group account and is not an invitation secret. The assistant can recommend only eligible decoded accounts; the on-chain invite still gates membership.

Point to the visible response mode. With no API key, show the deterministic fallback. If testing OpenRouter, show `openrouter` only after receiving that mode from the endpoint; natural-sounding text alone is not proof of a model call. Briefly demonstrate the privacy refusal with a synthetic email-shaped value, never a real wallet or contact detail.

Explain the boundary:

> GPT-4o may rerank and explain a bounded candidate set. It never receives private membership data, invents a group, signs a transaction, or controls funds.

There is no checked-in runtime catalog. If the program has no eligible Group accounts, show the honest empty result.

## Scene 3 — Create a circle and complete its roster (1:20–2:10)

Create a four-member circle:

- contribution: `100` demo USDC;
- cadence: demo-safe short period;
- members: four explicit wallet addresses;
- total round pot: `400` demo USDC;
- rounds: `4`.

Before approval, show the transaction preview: program ID, mint, contribution amount, cadence, roster size, and maximum possible collateral exposure. Explain that economic terms are immutable from `create_group`; the roster closes automatically when the final invited wallet calls `join_group`.

Until the create transaction builder is wired, state that the form validates economics but creates no account. Do not open an explorer link or imply a transaction occurred.

## Scene 4 — Join, reveal, and finalize the order (2:10–3:00)

Switch between member wallets or use prepared transaction signatures:

1. The creator submits a commitment in `create_group`; each invitee calls `join_group` with its own commitment.
2. The final join fills the roster and moves the Group to `Revealing`.
3. Members reveal nonzero 32-byte CSPRNG secrets that they kept private and persisted until confirmation.
4. An unprivileged wallet calls `finalize_order` after the full roster has joined and revealed.

Show that the payout order appears identically for every viewer. Explain that no keeper supplies the order; the program derives it from frozen commitments and verified reveals.

Be explicit about the MVP tradeoff:

> Commit-reveal makes the completed order auditable without an oracle. A last revealer can still abort a ceremony, so liveness-resistant randomness is a roadmap item.

## Scene 5 — Protection Ratio (3:00–3:50)

Show the rank-aware requirements for a four-member, 100-unit circle:

| Recipient | Required collateral |
| --- | ---: |
| Round 1 | 300 |
| Round 2 | 200 |
| Round 3 | 100 |
| Round 4 | 0 |

Activate only after required collateral is funded. Point to `Protection Ratio` and the separate `Collection status`.

Suggested narration:

> Protection Ratio covers remaining obligations of people who already received a pot. It is not a vague reputation score and it does not say the circle cannot stall. That is why collection health is shown separately.

## Scene 6 — Contribute and permissionlessly settle (3:50–4:50)

Have all four wallets contribute for round one. On the last contribution:

- show the paid/unpaid grid update;
- show the pot reach exactly `400`;
- use another wallet to call `settle_round`;
- show a correct-mint token account owned by the scheduled recipient receive exactly `400` (an ATA is conventional, not required);
- open the explorer transaction and the relevant program accounts.

Suggested narration:

> Solana does not run cron jobs inside a program. Settlement is permissionless: any keeper can submit it, while the program fixes the amount and recipient owner. A keeper may select one of that wallet's correct-mint token accounts, but cannot redirect funds to itself.

## Scene 7 — Cover the real failure mode (4:50–6:05)

Advance to a later round after the first recipient has already received the pot. Let that member miss the contribution deadline.

1. Show the wallet as overdue.
2. From an unrelated keeper wallet, call `cover_default`.
3. Show exactly one contribution move from the aggregate collateral vault into the pot vault and only the defaulter's `collateral_locked` ledger decrease.
4. Show the obligation labelled `Covered from collateral`, not `Paid on time`.
5. Call `settle_round` and show the scheduled recipient receiving the complete pot.
6. Reopen Protection Ratio and remaining collateral.

Suggested narration:

> The collateral is compensatory, not a fine. It replaces the missing contribution in the pot. The event history preserves the distinction, which becomes the raw evidence for a future opt-in contribution passport.

If the on-chain default path is not deployed and verified, present this as an interaction prototype and do not imply that the transfers occurred.

## Scene 8 — Agentic extension, with a safety boundary (6:05–6:40)

Open `GET /api/agent/manifest` and show `transactionMode`, the bounded supported-action metadata, the narrow collateral exclusions, and `signableTransactions: false`.

State that `transactionMode` is derived from whether a program ID environment value is present. It does not prove that the ID is deployed or that an RPC read occurred.

> The checked-in manifest is discovery metadata only: it never returns a transaction and does not claim Solana Actions compliance. Ringio's program surface is designed for future permissionless keepers, but the transaction-capable manifest, real simulator, and hosted keeper are roadmap. User-funded actions remain wallet-approved.

This connects the product to agentic engineering without pretending an LLM is required for custody or consensus.

## Close (6:40–7:00)

> Ringio's wedge is not “ROSCA, but on-chain.” It is an honest separation of solvency and liveness: fixed rules, visible collection health, and exact protection against the early-recipient default that breaks informal circles.

End on the repository, devnet program, app, and explorer links. If any is not public, label it `pending` instead of substituting an unrelated link.
